Phase 35: Project Tracker & Pluggable Professional Workflows Built

Documentation

Two connected ideas on the new Projects page. First, a real Projects table covering both employer and personal projects — a title, description, status, and (optionally) a real local repo_path. An employer project can optionally point at a real Phase 9 EmployerProjectAssignment via linked_assignment_id — that's never a second copy of its due date or email-tracking badge, just a reference, so the two never quietly drift apart.

Second, a Workflow Template: an ordered list of stages a project can link to for staged "what's done, what's next" tracking. Naming note: this is deliberately never called a "Skill" anywhere in the code, even though it started from a request to add a "skill uploader" — Phase 17 already has a real, unrelated Skill table (career proficiencies like "Python" or "public speaking"). A template is pure structured data — name, profession label, and an ordered list of stage titles/descriptions — never executable code, so importing one (paste the same JSON Export produces) carries none of the trust/sandboxing questions an actual software plugin would raise.

Marking a stage complete is always an explicit click — nothing here is ever inferred or auto-completed, the same rule Phase 9's email-seen badges already follow. The recommended next step banner is just the first stage (in order, filtered to whether you marked the project "new" or "existing") that doesn't have a completion record yet. Separately, if a project has a real repo_path, a suggested start banner does a best-effort check against real files on disk — e.g. a stage whose hint is "CLAUDE_PLAN.md and AGENT.md both exist" is checked literally. Most stages describe a process, not a file signature, so most of the time this honestly says "can't verify automatically, confirm yourself" rather than guessing — it's a starting point, never presented with the same confidence as a stage you actually checked off.

The built-in Software Development (IDE) template (seeded on demand, never force-recreated if you edit or delete it) is the user's own real described methodology: set up the project (new only) → caveman build, functionality first, theme second (new only) → build out the plan → describe each page's functionality → write that page's tests → agent-run the tests → manually run the tests. It exists specifically to prove the generic template mechanism works for something real, not just a schema nobody's data has gone through — any other profession's workflow (a Photoshop-based design pass, for instance) can be built or imported through the exact same UI, no code changes required.

Tutorial

  1. Open Projects, pick a profile, and click Seed built-in "Software Development (IDE)" template under Workflow templates.
  2. Click + Add project — pick Personal or Employer, give it a real title, and (if you want the repo-detection banner) a real local repo_path. Link the seeded template.
  3. Click Show stages & recommendation on that project — read the "Recommended next" banner, and (if you set a real repo_path) the "Suggested start" banner.
  4. Check a stage's box to mark it complete and watch the recommended-next banner move to the next stage; uncheck it and watch it move back.
  5. Try building your own template by hand under Workflow templates (add a few stages, any profession), or Export the built-in one and re-Import it as your own copy to confirm the round-trip is exact.

Project Parts (Steps 343–346) Built

A project isn't always one workstream with one methodology. The real example that motivated this: a high-rise construction project where plumbing, framing, and electrical crews all work concurrently, each following its own real process. A Part is a child of a Project — its own title, its own status, and its own optionally different Workflow Template — with its own independent stage checklist and recommended-next-step banner. A part is opt-in extra structure, never a replacement for the project's own top-level workflow: a simple, single-workflow project never needs one, and a project with parts can still (or instead) have its own top-level template linked, completely independently of what its parts are doing.

A part's repo_path is optional and falls back to the parent project's own when unset — useful for a monorepo-style project where one part (say, the backend) lives in its own subdirectory. Deleting a project cascades to its parts and their stage-completion records; deleting a single part never touches its siblings or the parent project.

Tutorial (parts)

  1. Expand a project (or add a new one) and scroll to its Parts section.
  2. Click + Add part twice — e.g. "Framing crew" linked to one workflow template, "Electrical crew" linked to a different one.
  3. Check off a stage on the framing crew's checklist and confirm its own recommended-next-step banner moves — and that the electrical crew's banner and progress count are completely unaffected.
  4. Change a part's status independently of the project's own overall status, and independently of its sibling parts.

Next steps

  • Add your own real employer or personal projects and link the seeded Software Development template to one you're actually working on.
  • Set a real repo_path on a project for a repo you actually have on this machine and see whether the suggested-start banner's guess matches where you'd actually pick up.
  • Try a second, hand-built template for a non-software profession (a rough Photoshop-based design pass, for instance) to confirm the mechanism really is generic, not secretly IDE-specific.
  • For an employer project, link it back to a real Phase 9 work assignment via linked_assignment_id so its due date and email-tracking badge stay in one place.
  • Try a real multi-crew (or multi-team) project with genuinely different processes per part — construction, a multi-discipline renovation, or a monorepo project with separate backend/frontend parts.
