Phase 30: Security Posture Guidance & Hardening Agent Built

What this is: real, hand-authored network security guidance on Security (home/private-device/work/public-network checklists, plus a dedicated warning for client/payment work over an untrusted network), and a real agent underneath it — an opt-in registry of routers/servers/other computers to watch (SecurityAuditTargets), read-only posture checks against them, and fix proposals that only ever change something after a separate, explicit confirm click — the same propose-then-confirm gate Phase 25's MaintenanceRuns already use, reused directly rather than a new mechanism.

Checks that actually run: for "this machine," a real firewall check (ufw status, honestly reported as unavailable where ufw isn't installed), real listening-port enumeration (ss -tlnp) diffed against a hand-curated expected baseline, a live check that the local backend is actually bound to 127.0.0.1 (not just a code-review assertion), and patch currency reused directly from Phase 6's own UpdateHistory. For a registered router/server with a stored SSH credential, the same connection code Phase 25 Step 169 already uses (never a second SSH client) runs a smaller, platform-appropriate check set. A check that can't run — no credential, tool missing, platform mismatch — is recorded honestly as an info-level finding saying so, never a guessed pass/fail.

Fix proposals: only one check type (an inactive local firewall) has a real, safe, automated remediation (sudo ufw --force enable) — everything else proposes "review this manually" with no command attached, since inventing a generic fix for a finding this system doesn't have a real, verified remediation for would be exactly the kind of fabrication this project avoids elsewhere. The one opt-in exception — auto-blocking a source IP after repeated failed local logins — is built and off by default, but honestly unexercised: dashboard.site has no login system yet, so there's nothing today that actually calls it.

Managed client sites (Step 241): both the WordPress plugin and Drupal module (Phase 25 Step 172) gained a real security-status verb — Drupal can precisely detect a security-specific update via core's own UPDATE_NOT_SECURE status; WordPress approximates it as "a core update is available, may include security fixes" since WordPress doesn't cleanly expose security-only status. Both also check for a default admin account and make a real outbound request to confirm whether sensitive paths (wp-config.php/settings.php, .git/HEAD, .env) are actually publicly reachable. Results land as ordinary SiteUpdateStatus rows tagged component_type=security, visible on Managed Sites.

Honest gaps: neither on-server agent's security-status verb has been exercised against a real WordPress or Drupal install (same caveat Phase 25's own agent already carries). Router-specific checks (OpenWrt/pfSense/Ubiquiti CLI commands) are a generic, best-effort fallback only, unverified against a real device. A security finding with no corresponding real remediation (e.g. "default admin account exists") can be proposed through the same Maintenance Runs mechanism but will honestly fail to confirm — there's no "rename this account" action to run, which is correct behavior, not a bug. See CLAUDE_PLAN.md's Phase 30 for the full annotated build.

Tutorial

  1. Open Security from the side menu and read the guidance section for whatever network you're actually on right now.
  2. Under Audit targets, click + Add target — check "This machine" for a zero-config local scan, or add a router/server with a label and host.
  3. For a remote target, click + SSH credential to store how to reach it (never a raw password/key in the vault database — it goes through the same keyring pattern every other credential in this project uses).
  4. Click Scan now, then View findings to see the real results.
  5. On a finding, click Propose fix, review what it actually says it will do, then Confirm & apply only when you mean it.
  6. On Managed Sites, a site with the on-server agent installed can run a security check the same way it already runs an update check.

Next steps

  • Smoke-test the WordPress/Drupal security-status verb against a real staging install.
  • Add a real login system to dashboard.site so the auto-block-IP exception has something to actually protect.
  • Add device-specific checks for real router platforms (OpenWrt/pfSense/Ubiquiti) once one is available to test against.
