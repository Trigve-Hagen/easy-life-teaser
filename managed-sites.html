Phase 25: Managed Client Websites — Preview

Documentation

What this is: private tooling for actually running the maintenance side of the Global Web Methods (Phase 14) freelance business — the real client sites the user maintains, how to securely reach each one, and (with explicit confirmation) how to apply a real update. This lives in personal_vault.db like every other profile/company-scoped table, not a separate public service.

Adding a site: pick a Profile and Company on the Managed Sites page, then + Add site — client name, site URL, and CMS type (WordPress, Drupal, or Other/none). cms_type = other is a real, honest state: there's no update checker for it, used here for infrastructure that isn't a client CMS site at all (this project's own EC2 test instance, for example).

Credentials: click Manage on a site, then + Add credential. An SSH credential's secret (password or private key) is stored via the OS keyring the moment you save it and is never shown again — the list only ever shows whether a secret is stored, never its value. An AWS SSM credential instead records the instance id/region, since SSM access is governed by IAM permissions rather than a stored secret.

Checking update status (Step 169): click Check for updates on a managed site. For WordPress/Drupal sites with a stored SSH credential, this connects over SSH and runs wp core/plugin/theme or drush pm:updatestatus — read-only, it never applies anything. If there's no checker for this site's CMS type, no SSH credential stored, or the connection fails, it says so honestly instead of reporting a fabricated "up to date" result — the reason is shown right under the button.

The on-server agent (Step 172): most budget/shared hosting never allows SSH at all. site_agent/ (repo root, sibling to backend/) has an installable WordPress plugin and Drupal module exposing the same status data locally, plus backup/update actions, protected by a per-site API key generated at install time. Installing it is a manual, one-time step done directly on that client's hosting — nothing in this project automates that install. Once installed, add its API key here as a agent_api_key credential.

Proposing and applying a real update (Step 173): once a component shows outdated, click Propose update — this only ever reads the most recent Check for updates result, it never invents an available update. The resulting run needs a second, separate click, Confirm & apply, which is the only action anywhere in this phase that can change a client's live site: it calls the on-server agent's backup endpoint first, and only calls update if that backup call actually returned a reference. If the backup fails or returns nothing, the run is marked failed and update is never called — no exception for "just a minor plugin bump." Every run, applied or not, stays visible in the Maintenance runs log afterward.

Backups now cover files, not just the database, and can be rolled back (Step 231): a run's pre-update backup archives the specific plugin/theme/module directory (or wp-admin/wp-includes for a WordPress core update) alongside the database dump, in one archive on the client's own server. Any updated or failed run with a live backup gets a Roll back button — a second, separate, explicit click that restores both the files and the database to exactly how they were beforehand. Rollback is never automatic, even when an update itself just failed.

Storing a backup off the client's server (Step 232): a backup sitting only on the same server that's about to be updated isn't much of a safety net if that update — or the server — fails badly. Click Store backup next to any run with a backup reference to download it and keep a copy either on a registered external drive (the same ExternalDrives registry the Archive page uses, with a real free-space check first) or in the local vault's own storage on this machine. Every stored copy shows up in the Stored backups list per site, with exactly where it lives.

Tutorial

  1. Open the Managed Sites page, pick a profile and company.
  2. Click + Add site and register a real client site (or a test entry, with CMS type Other/none).
  3. Click Manage on it, then + Add credential to store how the vault should reach it.
  4. Click Check for updates — for a WordPress/Drupal site with a working SSH credential, review the real component list; otherwise read the honest reason it couldn't check.
  5. For a site where no SSH access exists, follow site_agent/README.md to install the on-server agent on that CMS, then store its API key as an agent_api_key credential here.
  6. On an outdated component, click Propose update, review the from/to versions, then click Confirm & apply — watch the run move through backup, then update (or fail with a clear reason), in the Maintenance runs log.
  7. Click Store backup on that run and choose Local vault or an External drive — check the Stored backups list to confirm it landed.
  8. If an update goes wrong, click Roll back on the run and confirm — watch its status become rolled_back, or read the honest error if the on-server agent couldn't be reached.
