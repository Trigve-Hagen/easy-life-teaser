Phase 40: Log Search & Live Tail Built

Read this first, because it shapes everything below: this is a poll, not a live stream, and nothing is installed on any server to make it work. A real log platform ships a forwarder daemon onto every host. This project has committed never to install an agent on a server, so log lines are pulled over connections that already exist — the same SSM tunnel and SSH that deploys and health checks already use. The honest consequence is a real latency floor: new lines appear after the next poll, not instantly. The page says so in those words rather than calling itself a live tail.

Documentation

The Logs page searches log lines from the servers you run and the client sites you manage. Reach it from the side menu, or from the Logs button sitting next to Server Infra on any row in Managed Sites, which opens the page already scoped to that one site.

  • Filters, deliberately not a query language. Source, time range, level, status class (2xx/3xx/4xx/5xx), method, client IP, path, and free-text search over the raw line. A half-working query language that silently mis-parses is worse than none, so that was decided against in writing rather than drifted into. Every filter lives in the page's URL, so a filtered view can be bookmarked or shared and survives a reload.
  • A timeline strip above the results, which is how you find a spike before you know what to search for. Empty buckets are drawn as gaps — the histogram never compresses quiet periods out of existence to make the bars look denser.
  • Patterns. The same lines grouped by shape, so a few thousand rows read as a handful of real things (in testing, 1,193 lines collapsed to 3). This is plain deterministic string work computed on your own machine. Log lines are never sent to any AI model — a log line carries a real visitor's IP address, the URL they requested and their user-agent, which this project's application/agent split does not allow near a model.
  • Secrets are stripped at ingest, before anything is written down. Bearer tokens, secret-bearing query parameters, AWS key ids and private-key blocks are replaced with a visible [redacted] marker, and the row is flagged so you can tell a redaction apart from text that was literally there. Not hypothetical: real credential-probe traffic already appears in these logs.
  • Sources are discovered, never assumed. A log path that does not exist, or that the stored SSH user cannot read, produces no source at all and says why — it is never given an empty row that looks like "nothing happened". A client site with no SSH credential simply reports that, plainly.

What works across platforms, and what does not. The web-server access log is the same everywhere — nginx and Apache do not care whether WordPress, Drupal, ASP.NET Core or anything else sits behind them — so that part generalises with no per-platform work. Application logs differ, and are handled by where the log lives rather than by which CMS it is: a WordPress site's PHP error log is an ordinary file; Drupal's default logging is a database table (core's dblog module writes to watchdog, so there is nothing to tail and it is read as a query instead); and IIS/ASP.NET on Windows is registerable but cannot yet be read — that needs WinRM rather than SSH, and is not built. An ASP.NET Core app behind nginx on Linux works today with no special handling.

Tutorial

  1. Open Logs from the side menu.
  2. Click Register this server's own logs to add the shared instance's nginx access log and each backend service's systemd journal.
  3. For a client site, open Managed Sites, click Logs on that site's row, then Find logs on this client site. If the site has no stored SSH credential, it will tell you so rather than appearing to work.
  4. Click Fetch now for an immediate pull, or wait for the scheduled poll. This opens a real connection and takes a few seconds.
  5. Set Status to 5xx server error and click Apply — note the filter appears in the address bar, so you can bookmark this exact view.
  6. Read the Patterns table before scrolling the raw rows. It usually answers the question faster.
  7. Expand raw on any row to see the exact stored line.
  8. Click ← Back to return where you came from.

Next steps

  • Run one real poll against a real host and confirm actual lines land — every transport path is currently proven against tests, not against a live server.
  • Check the What is kept line before concluding something did not happen: an empty result older than the retention window is the limit, not an absence of events.
  • If you manage Windows/IIS sites, decide whether the WinRM transport is worth building before relying on this for them.
