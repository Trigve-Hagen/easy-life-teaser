Phase 34: Capacity Gating, Multi-Region Scaling & Internationalization In progress

Documentation

What's real so far — Step 281, the Server Infra page: Server Infra shows real, read-only numbers pulled from the shared "Global" EC2 instance every 5 minutes by an installed cron job (backend/infra_monitor_agent.py + backend/scripts/run_infra_snapshot.py), over the same SSM tunnel the deploy scripts already use — never a new credential path. It shows: disk space used/free, and one row per deployed app/service (gwm_site, product_backend, marketplace_backend, and lifemodel-backend, which also runs on that shared instance but — confirmed by direct inspection — isn't routed by nginx, so it's shown with a "not nginx-routed" badge rather than hidden) with its size on disk, which systemd service (if any) runs it, and whether it's actually up right now. It also shows real per-page hit counts parsed from the nginx access log, attributed to whichever service nginx's own routing sends that path to — a running total plus a "last 5-minute window" figure, deliberately labeled "recent unique IPs" rather than "concurrent viewers" since a passive log parse can't measure that, and stated plainly as raw counts that include bots/scanners/probe traffic (a real /.env credential-probe line shows up correctly, not filtered out). Adding a new site/service to this page is a one-line entry in infra_monitor_agent.py's SITES list — nothing else needs to change.

Also real — Steps 283-285: the same Server Infra page now also shows Managed client sites (Step 283) — every Phase 25 client site with a stored SSH credential gets a real disk reading here too, reusing Step 169's exact SSH connection code; a site with no SSH credential shows "not monitored," never a guessed number. A View Server Infra link on each site's card in Managed Sites deep-links here. Every not-active registered service now gets one automatic, logged, rate-limited restart attempt per poll (Step 284, capped at 3/hour — past that it's flagged "needs manual attention" instead of retried forever). And a new OS packages panel (Step 285) shows real upgradable/orphaned package lists detected every poll — actually applying an update or removal always requires a separate Propose then Confirm & apply click, the same propose-then-confirm split Phase 25 Step 173 already uses, deliberately not loosened just because it's our own shared instance.

Also real — Steps 287-288: the OS packages panel now has a sibling Application dependencies panel showing each of our own services' outdated pinned Python packages (from their own requirements.txt, as actually installed) — a distinct layer from OS packages, detection-only, no apply mechanism. Every outdated package (OS or app-level) now carries a real, computed risk badge (Step 288) — a major-version jump is "breaking likely," a minor/patch bump is "likely safe" — verified live against a real case: bcrypt 4.3.0 → 5.0.0 on marketplace_backend was correctly flagged. A "breaking likely" (or unfetchable-comparison "unknown") package is excluded from the routine bulk **Propose** action by default and needs its own individually-named "review and propose anyway" click. A **View changelog** button fetches a real changelog on demand (Debian's for OS packages, PyPI's for app packages) — never eagerly on every poll, since a single package's changelog can run hundreds of KB.

Still planned, not built: the client-capacity threshold gate and signup-closed messaging (Steps 275-276), reviewed AWS provisioning and data migration to new instances (Steps 277-278), signup geolocation and new-country expansion signals (Step 279), and the language switcher (Step 280). See CLAUDE_PLAN.md's Phase 34 for the full step-by-step design, including the real EC2 instance numbers (2 vCPUs, ~1GB RAM, already using swap) that grounded the plan.

Tutorial

  1. Open Server Infra from the side menu.
  2. Read the disk gauge at the top — used vs. free space on the shared instance, as of the last poll.
  3. Scroll to "Deployed apps & services" — each row shows a real size, service name, and a running/stopped badge (plus a note if it was recently auto-restarted).
  4. Scroll to "Managed client sites" — a Phase 25 site with an SSH credential on file shows its own real disk usage here.
  5. Scroll to "OS packages" — review the real upgradable/orphaned lists, click Propose, then Confirm & apply only when you actually want that change applied.
  6. Scroll to "Page hits" — expand a site's list to see real per-page request counts, most-hit pages first.
  7. Click Refresh now to trigger a poll immediately instead of waiting for the next 5-minute cron run.
