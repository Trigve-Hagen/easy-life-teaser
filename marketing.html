Phase 11: Company Registry & Marketing Plan Agent — Preview

Documentation

Adds a Company registry — a company is owned either by a profile you control (employee_owned) or by a real Phase 9 Employer (employer, optionally linked to a Phase 10 Business for real financials). Each company gets one or more named marketing plans made of MarketingPlanElement rows — target-audience notes, messaging, one row per channel, an optional budget line, and KPI targets — plus a MarketingResult log for recording real metrics against any element later. The marketing agent (marketing_agent.py) drafts a full plan skeleton from a plan name, target audience, goals, and a channel list: every element it creates lands at status="draft", nothing is ever auto-published or auto-spent. For an employee_owned company, a requested budget line calls the real Phase 8 budget engine and suggests 10% of the profile's actual positive monthly surplus. For an employer company, the agent may only read that business's numbers through a valid Phase 10 EmployeeAccessGrant — the exact same default-deny gate the Business Stats shared-summary view enforces, no exceptions for marketing — and suggests 5% of the most recently reported (and shareable) profit.

Steps 32–35/55 add employer-side workforce coordination on top of the core plan tooling: Work assignments can only go to a Phase 9 participant who is already opted_in on their profit-share proposal — assigning work only requests tracking, it never grants it, and only the assigned person can move tracking_consent to opted_in. Once consented, progress syncs through progress_tracker.py or the dashboard directly, gated on both that consent and a matching, active, opaque WorkerDevice registration — never keystroke logs, screenshots, screen recording, browser history, or file-content scraping, regardless of what an employer might ask for. Revoking a device makes its very next sync fail closed. The performance monitor gives the employer a read-only rollup (total time logged, latest task-completion percentage, optional per-device breakdown) — visibility only, never an automated action — and every load is written to the linked business's access audit log so a participant can always see who looked, and when. Territories describe a marketing target (a place or demographic, never a location a device must physically sit in) with minimum hardware requirements; a TerritoryContract only moves to accepted once the linked device's real specs are checked against those minimums — reject, never a silent pass.

Tutorial

  1. Open the Marketing page and pick a profile.
  2. For an employee-owned company: create one with type Employee-owned, then use Generate a draft plan — a plan name, target audience, goals, and a comma-separated channel list (e.g. Content/SEO, Social Media, Email List). Leave the budget checkbox on for a suggestion sourced from that profile's real Budget page numbers.
  3. For an employer company: first add a real Employer and, if you want business-backed numbers, a Business linked to it with an access grant. Create the company with type Employer, its Employer ID, and (optionally) the Business ID. Generating a plan now requires that Business Stats access grant's ID — try it without one first and confirm it's rejected.
  4. Review the drafted elements — each has an editable status (draft → proposed → active → paused/completed) you move by hand as the plan actually happens.
  5. On an employer company, open Work assignments and assign work to an opted-in participant. Open the assignment, move tracking_consent to opted_in, register a device, and log a progress metric — notice logging is blocked until both are true.
  6. Click Load performance monitor to see the rollup, then check the linked business's Access Audit Log on the Business Stats page — your read just showed up there.
  7. Add a Territory with minimum hardware requirements, propose a contract with a weak device and watch it get rejected on Accept, then propose one with a device that actually qualifies.

Marketing Plan Creator (Steps 299–305) Built

A real, structured plan builder layered on top of the same Company/plan-element tooling above. A MarketingPlan row (Step 299) holds actual targeting fields — area_type (city/county/state/country) plus a real area_value, a free-text demographic, and an ISO-639-1 language code — replacing the old plan-name-string-only grouping (existing plans keep working unchanged; new ones get a real parent row). The channel/action-type choice reuses Phase 15's existing CampaignActionTypes catalog rather than a second list.

Step 300 adds real image/video upload per plan (MarketingPlanMedia, stored under this app's AppData directory like every other uploaded file in the vault) and a Draft copy with agent button — marketing_agent.draft_copy() always produces a real deterministic draft grounded in the plan's own area/demographic/language fields, and rewrites it through a local Ollama model when one is actually configured and reachable, with an honest note when it isn't (never a silent, uncredited English fallback presented as the requested language).

Step 301's marketing_creative_agent.py composes real creative from what you uploaded — an HTML email body with your images embedded, a JPEG ad image with the drafted headline overlaid (Pillow), or a video with a caption burned in (a real, locally-installed ffmpeg binary). This is deliberately compositing only: it never calls a text-to-image or text-to-video model to invent new visual content from nothing, the same boundary Phase 31's avatar widget draws for a different kind of media. No ffmpeg on this machine means the video option honestly fails rather than fabricating a result.

Steps 302–303 solve the actual hard problem: an employer's plan and an employee's own local vault are two different databases on two different machines, and no server in this project may ever write into either one directly. Sending a plan queues a plain-JSON snapshot (plus base64-encoded media) in product_backend's own PendingMarketingPlanAssignments table — the exact same "queued, never pushed" pattern Phase 33's PendingPointAwards already established — keyed to both accounts' real emails, and only after checking the target participant's assignment is tracking_consent=opted_in and their device is still active. The employee's own vault pulls it in on its own next check-in (Pull plans sent to me), creating real local rows from the snapshot; product_backend's involvement ends at queuing. Deploying a pulled plan reuses Phase 15 Steps 225–227's existing email/blog/ad send paths completely unchanged, using the employee's own connected accounts — a pulled plan never carries the employer's credentials — and reports real status back through the same queue, in reverse.

Tutorial

  1. On a company, open Marketing Plan Creator and click + New plan — set an area type/value, an optional demographic, and a language code.
  2. Open Manage on the plan, click Draft copy with agent, then upload an image and click Compose for the ad-image channel — download the result and confirm it's a real composited JPEG.
  3. On an employer company with an opted-in, device-registered participant, fill in Send to employee with both accounts' real emails and send — note the returned relay assignment ID and pending status.
  4. Switch to the receiving account's own company and click Pull plans sent to me with that same employee email — confirm the plan, its messaging, and its media all now exist locally.
  5. Deploy the pulled plan's campaign action exactly as you would a self-authored one, then check back on the sending side — the status should now read deployed with a real result note.

GitHub Export & Rented-Compute Dispatch (Steps 306–308) Built

An escape hatch for the one real limit Step 302's relay has: product_backend embeds a plan's media as base64 text in its own shared database — fine for a photo or two, a bad fit once a plan's real media crosses a size where you'd rather keep it off shared infrastructure entirely, or if you just want a persistent, reusable copy outside LifeModel. On a plan's Push to GitHub panel, Download push script gets you a real, standalone Python script (stdlib only) — run it locally and it fetches this plan's current real data from your own backend, asks for your own private repo's URL and a GitHub personal access token at run time (never stored anywhere, not even in the script itself), and reports the real resulting repo/commit back here automatically. Once a plan has been pushed, Send to employee automatically switches to sending a tiny pointer (repo URL + commit) instead of the full payload — the receiving side clones the repo fresh on its own next pull, so the real media bytes travel employer → GitHub → employee, never through product_backend at all.

Step 308 reuses that same pointer as a new, closed RentalJobs job type on the Phase 18 compute marketplace — marketing_creative_compose — so a company with an active rental agreement can dispatch a plan's ad-image or video captioning to a rented stranger's machine instead of running it locally. The rented machine only ever gets a single-repo-scoped, revocable GitHub deploy key (never a broader credential, never anyone's LifeModel account) and only ever runs Step 301's own real compositing code (Pillow/ffmpeg, vendored onto the worker machine as a real companion file since it can't reach this repo directly) — it commits the real composed result back to the same repo and reports the new commit as its result. It can never send an email, post an ad, or publish anywhere; that stays exactly where Step 303 already put it, on the employer's or employee's own machine.

Tutorial

  1. On a plan with at least one uploaded image, open its panel and click Download push script under Push to GitHub.
  2. Create a free private repository on your own GitHub account first (LifeModel never creates one for you), then run the downloaded script — enter that repo's URL and a fine-grained, repo-scoped personal access token when prompted.
  3. Refresh the plan panel — it now shows the real repo/commit it was last pushed to.
  4. Use Send to employee as usual — the relay assignment now carries the lightweight GitHub pointer, visible in its queued payload, instead of embedded media.
  5. On the receiving side, Pull plans sent to me as usual — if the repo is private, paste a token in the pull form's optional field first.

Marketing Plan Modules (Steps 315–317) Built

A content-package marketplace built fresh on top of product_backend rather than reusing Phase 26's still-unbuilt generic Modules/code-bundle system — a MarketingPlanModuleListing is a plan someone else made, packaged for others to install, not executable code. It comes in exactly two shapes, enforced structurally rather than by a runtime check: a plain hosted_bundle listing (JSON uploaded straight to product_backend, capped at 20MB, downloaded directly) for a text-only plan, or a marketing_plan_with_video listing that can only ever pair with storage_type="github" — it reuses Step 306's own push script unchanged, so no video byte ever touches product_backend's disk; the seller just pastes back the resulting repo URL. A new listing always starts pending_review and only becomes publicly listed through an explicit approve step (documented here, like every other spot in this project, as real but not yet gated behind actual admin auth).

On gwm_site's Modules page, a signed-in seller uploads either shape and can see and approve their own pending listings. Back here on Marketing Plan Modules, every listed module — hosted or GitHub, mixed together in one catalog — shows up with three separate, explicit WordPress-style actions. Download and Install are, honestly, the same real fetch under the hood (a direct download for a hosted bundle, a real read-only git clone for a GitHub one) — both just show you exactly what's inside (plan name, targeting, every element title, every media filename) before anything is written, which is the whole point of separating them from Enable. Enable always re-fetches the module's real current content itself rather than trusting whatever Preview already showed on screen, then creates the actual local MarketingPlan/MarketingPlanElement/MarketingPlanMedia rows on the company you pick — the exact same row-creation logic Step 303's employee-pull path uses, so the two paths can never quietly drift apart.

Tutorial

  1. On gwm_site's Modules page, sign in and upload a small plan JSON on the Plain tab, or paste a repo URL/ref you already pushed with Step 306's script on the Video tab.
  2. On the Mine tab, click Approve on your new listing so it becomes publicly listed.
  3. Back here on Marketing Plan Modules, pick a profile and company, click Refresh list, and find your listing in the catalog.
  4. Click Download or Install — either one fetches the real content and shows you its plan name, elements, and media filenames.
  5. Click Enable — confirm a real new marketing plan now exists on the company you picked, on the Marketing page.
